# SafeVault 多电脑协作与发布更新规范

## 1. 唯一版本来源

- GitHub 仓库：`https://github.com/1510952971/safevault`
- 正式分支：`main`
- 版本判断以 `git log -1 --oneline` 和 GitHub `main` 的提交号为准。
- 不以某台电脑上的旧 `dist`、旧桌面快捷方式或旧 NAS 文件夹作为版本依据。

## 2. 文件分工

| 文件或目录 | 是否同步到 GitHub | 处理规则 |
| --- | --- | --- |
| `src/`、`electron/`、`server/` | 是 | 正常提交和拉取 |
| `package.json`、`package-lock.json` | 是 | 依赖变化必须一起提交 |
| `tests/`、`docs/`、`.bat` | 是 | 流程和规范变更一起提交 |
| `node_modules/` | 否 | 每台电脑运行增量依赖安装 |
| `dist/assets/` | 否 | 每台电脑运行 `npm run build` 生成 |
| `deploy/zspace-package/` | 否 | 每次发布 NAS 前重新生成 |
| `data/`、NAS 映射的数据目录 | 否 | 密码数据只保留在本机或 NAS，禁止提交 |

这样可以避免把某台电脑的构建缓存、依赖目录或密码数据库误传到 GitHub。

## 3. 修改电脑：发布到 GitHub

在开始修改前：

```bash
git checkout main
git pull --ff-only origin main
```

修改完成后，必须按顺序检查：

```bash
npm install --prefer-offline --no-audit --no-fund
npm test
npm run build
git status
```

确认 `git status` 中只有本次要发布的代码、文档或脚本文件后：

```bash
git add <本次修改的文件>
git commit -m "清晰描述本次更新"
git push origin main
```

推送完成后记录提交号：

```bash
git log -1 --oneline
```

不要使用 `git push --force` 覆盖远程历史。

## 4. 其他电脑：获取 GitHub 更新

已有项目目录：

```bash
git checkout main
git pull --ff-only origin main
npm install --prefer-offline --no-audit --no-fund
npm run build
```

也可以直接运行项目根目录的 **`同步最新代码.bat`**。该脚本会在发现未提交改动时停止，避免误覆盖本地代码。需要同步后立即启动最新桌面端时，运行 **`更新并启动桌面客户端.bat`**。

新电脑：

```bash
git clone https://github.com/1510952971/safevault.git
cd safevault
npm install --prefer-offline --no-audit --no-fund
npm run build
```

桌面端使用 **`启动桌面客户端.bat`**。该脚本会先切换到脚本所在目录，再执行生产构建，避免电脑项目路径不同导致找不到依赖或资源。

每台电脑建议只保留一个 SafeVault 项目副本，并从该副本运行脚本、创建桌面快捷方式。若电脑上已经打开旧版本，使用 **`更新并启动桌面客户端.bat`** 会让已存在的单实例重启并加载最新 `main.cjs` 和 `dist`；普通重复启动仍只激活已有窗口。

## 5. 极空间 NAS：发布构建产物

在已拉取最新 `main` 的电脑上运行：

```text
生成极空间部署包.bat
```

脚本只更新本地部署包中的 `dist` 和 `server`，不会删除 `deploy/zspace-package/data`。

上传到极空间时只覆盖原 SafeVault 目录中的：

- `dist/`
- `server/`

然后在极空间 Docker 中重启原容器。严禁删除或覆盖：

- 极空间原有的 `data/`
- 容器映射到 `/app/data` 的目录
- 原有容器后再重新创建一个没有数据挂载的新容器

更新后访问：

```text
http://NAS地址:8088/api/version
```

应返回服务版本、健康状态和 `userCount`。如果 `userCount` 变成 `0`，先停止操作并检查 `/app/data` 是否仍然映射到原数据目录，不要重新注册账号。

## 6. 每次发布前的最小验收清单

- [ ] `git branch --show-current` 为 `main`
- [ ] `git pull --ff-only origin main` 成功
- [ ] `npm test` 通过
- [ ] `npm run build` 通过
- [ ] `git status` 没有意外的密码库、日志或临时文件
- [ ] GitHub 远程提交号与本机 `git log -1` 一致
- [ ] NAS 更新只覆盖 `dist`、`server`
- [ ] NAS 的 `data` 映射未改变
- [ ] 重启后 `/api/version` 正常，`userCount` 未异常归零

## 6. 极空间账号同步、备份与远程地址

SafeVault 的多端同步以极空间 Docker 为唯一数据中心：

- 每台设备使用同一个极空间同步账号登录；主密码只在设备本地参与派生，NAS 保存的是认证摘要和加密金库密文。
- 云端每次推送都会携带当前版本号。设备基于旧版本推送时，服务端返回 `VERSION_CONFLICT` 并拒绝覆盖；客户端必须先重新拉取极空间权威数据，再继续操作。
- 每次数据库写入都会先在独立映射目录 `safevault-backup/database/` 保存完整副本；用户历史版本保存在 `safevault-backup/users/`，两类备份默认各保留最近 30 份。
- 极空间 Docker 必须把 `Docker/safevault-backup` 单独映射到 `/app/backup`。升级时同时保留 `data/` 和 `safevault-backup/`；若 `data/` 整体丢失，服务启动时会从外部最新备份自动恢复。

远程访问地址规则：

- 极空间打开 SafeVault 后出现的 `http://127.0.0.1:xxxxx` 是当前电脑的临时代理通道，不是 SafeVault 账号地址；不同电脑、不同启动会出现不同端口是正常的。
- 页面端始终跟随当前网页地址。客户端发现已保存的旧地址与当前页面都是本机代理时，会自动丢弃旧端口并使用当前页面，不需要重新注册账号。
- 如果登录提示“当前极空间代理指向了另一份 SafeVault 数据库”，这不是端口问题，而是远程访问实际到达了另一容器或另一数据目录。必须把 safevault 容器的同一个 NAS 文件夹持续挂载到 `/app/data`，不要删除容器重建新数据卷。
- 如果旧远程访问链接能登录、新链接提示账号已注册但认证失败，先把远程访问条目的目标恢复为旧的可用目标（例如 `127.0.0.1:<宿主机端口>`），不要直接换成 NAS 局域网 IP；这通常表示两个目标没有指向同一容器或同一 `/app/data`。
- 只有直接从 Windows 桌面端访问固定地址时，才需要在“极空间 NAS 同步”中填写固定的 NAS 域名/HTTPS 地址；不要把某台电脑的 `127.0.0.1:xxxxx` 复制到另一台电脑。

主密码与同步账号认证关系：

- 注册同步账号时，NAS 只保存由“账号 + 主密码 + 账号盐值”派生出的认证摘要，不保存主密码明文。
- `v1.2.2` 起，使用“修改主密码并重加密”会先推送新密文，再同步更新 NAS 认证摘要；多台电脑随后统一使用新主密码登录。
- 如果某个账号曾在 `v1.2.2` 以前修改过主密码，旧版本可能只改了本地密文、没有更新 NAS 认证摘要。此时应使用注册同步账号时的原主密码登录已部署的旧版本/仍在线设备，再升级到 `v1.2.2` 后重新执行一次主密码修改；不要重复注册账号，也不要覆盖 `data/`。
