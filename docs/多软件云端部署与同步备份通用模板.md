# 多软件云端部署、同步备份与迁移通用模板

> 用于甲骨文云、AWS、其他 VPS 或 NAS 上部署多个软件。
> SafeVault 的 `nas.985251.xyz` / `safevault.985251.xyz` 只作为示例，新增软件时必须替换成自己的值。

## 1. 设计目标

这套方案解决四件事：

1. 一个服务器承载多个软件，但软件之间互不污染；
2. 每个软件有独立域名、容器、数据目录和备份目录；
3. 主服务器故障时，可以从第二端恢复或切换；
4. 更新、迁移、回滚时不误删业务数据。

核心原则：

- 只共享入口层（DNS、Cloudflare、Caddy、Docker 网络），不共享应用数据卷；
- 业务容器不直接暴露到公网，只由公共 HTTPS 反向代理转发；
- “同步”优先使用软件自己的 API、导出包或数据库备份，不直接复制正在运行的数据库文件；
- 主备互备不是无冲突的双主同时写入，必须有明确的主端、版本号和冲突处理规则；
- 任何迁移前先备份、验证备份，再切换 DNS，旧服务器和旧数据在验收完成前不能删除。

## 2. 推荐架构

```text
用户/客户端
    │ HTTPS
    ▼
Cloudflare DNS / Tunnel
    │
    ▼
公共 Caddy（只负责证书、域名分发、HTTPS）
    ├── app-a.example.com ──► app-a 容器 ──► app-a/data
    ├── app-b.example.com ──► app-b 容器 ──► app-b/data
    └── sync.example.com  ──► 同步服务容器 ─► sync/data

每个软件独立：
    data/       运行数据
    backup/     本软件备份
    config/     非秘密配置
    secrets/    密钥和密码（不进 GitHub）
```

公共 Caddy 可以服务多个软件，但每个软件必须使用独立的子域名和反向代理块。Caddy 故障只影响入口，不应导致任何软件的数据目录混用。

## 3. 域名和子域名规划

假设主域名为 `${ROOT_DOMAIN}`，软件标识为 `${APP_ID}`：

| 用途 | 示例 | 规则 |
| --- | --- | --- |
| 用户界面 | `${APP_ID}.${ROOT_DOMAIN}` | 对外提供 Web/App 访问 |
| API/同步 | `api-${APP_ID}.${ROOT_DOMAIN}` | 只有软件需要独立 API 域名时使用 |
| 管理后台 | `admin-${APP_ID}.${ROOT_DOMAIN}` | 默认不公开，优先 VPN、Cloudflare Access 或内网 |
| 监控状态 | `status.${ROOT_DOMAIN}` | 可选，不放敏感数据 |

要求：

- 一个子域名只指向一个软件入口；
- 不要让多个软件共用同一个 `/api` 路径；
- Cloudflare Tunnel 主机名、Caddy 路由和容器名称要一一对应；
- 新增软件只添加新的子域名和代理块，不修改已有软件的数据挂载；
- 记录 DNS、Tunnel、Caddy、容器和端口的对应关系。

## 4. 服务器目录标准

推荐使用 `/opt/apps` 存放业务，使用 `/opt/infra` 存放公共基础设施：

```text
/opt/
├── infra/
│   ├── caddy/
│   │   ├── Caddyfile
│   │   ├── data/
│   │   └── config/
│   └── monitoring/
└── apps/
    ├── ${APP_ID}/
    │   ├── compose.yml
    │   ├── .env                 # 不提交 GitHub
    │   ├── config/              # 非秘密配置
    │   ├── data/                # 业务主数据
    │   ├── backup/              # 本软件独立备份
    │   └── secrets/             # 密钥，权限 600
    └── ${OTHER_APP_ID}/
```

每个软件只能挂载自己的目录：

```text
/opt/apps/${APP_ID}/data   -> 容器内 /app/data
/opt/apps/${APP_ID}/backup -> 容器内 /app/backup
```

禁止：

- 多个软件共同挂载 `/opt/apps/shared-data`；
- 把一个软件的 `data` 挂到另一个软件的 `/app/data`；
- 把密码、Token、私钥、数据库和用户上传文件放进 Git 仓库；
- 为了更新而删除整个应用目录或重新创建没有数据挂载的容器。

## 5. Docker Compose 通用骨架

每个软件一份 Compose 文件，容器只暴露给公共网络，不直接映射公网端口：

```yaml
services:
  ${APP_ID}:
    image: ${IMAGE}:${TAG}
    container_name: ${APP_ID}
    restart: unless-stopped
    expose:
      - "${APP_PORT}"
    env_file:
      - .env
    volumes:
      - ./config:/app/config
      - ./data:/app/data
      - ./backup:/app/backup
    networks:
      - public-proxy

networks:
  public-proxy:
    external: true
```

公共 Caddy 只添加对应路由：

```caddyfile
${APP_ID}.${ROOT_DOMAIN} {
    reverse_proxy ${APP_ID}:${APP_PORT}
}
```

如果 Caddy 与应用不在同一台服务器，改用 Cloudflare Tunnel 或内网地址转发，但仍保持每个软件独立的目标和端口。

## 6. 同步与备份方案

### 6.1 推荐的主备模型

适合密码库、配置中心和重要个人数据：

- 主端：日常读写的服务器或 NAS；
- 备用端：另一台服务器、NAS 或对象存储；
- 写入主端成功后，复制加密数据或备份包到备用端；
- 主端故障时切换到备用端；
- 主端恢复后，先比较版本、时间戳和数据指纹，再把最新版本复制回去。

两个端点可以使用同一组逻辑账号，但服务器上的账号记录和数据库仍然独立。只有完成端点登录、初始化复制和版本校验后，才算建立互备。

### 6.2 不同软件选择不同同步方式

| 软件类型 | 推荐方式 | 不推荐方式 |
| --- | --- | --- |
| 密码库/加密笔记 | 应用层加密同步、版本锁、冲突检测 | 直接复制明文数据库 |
| PostgreSQL/MySQL | `pg_dump`/`mysqldump`、主从复制或应用导出 | 直接 rsync 正在运行的数据文件 |
| SQLite 软件 | 停机后复制或使用软件导出 | 在线复制 `.db` 文件 |
| 文件管理/相册 | 增量文件同步、快照、校验和 | 多端同时覆盖同一文件 |
| 配置服务 | 加密配置备份、GitOps、版本化导出 | 把 `.env` 和 Token 提交 GitHub |

### 6.3 备份最低标准

采用 3-2-1 原则：

- 至少 3 份数据副本；
- 至少 2 种存储介质；
- 至少 1 份在另一台设备或另一地点。

每个软件至少保留：

```text
主数据：/opt/apps/${APP_ID}/data/
本机灾备：/opt/apps/${APP_ID}/backup/
异机/离线备份：另一台 NAS、对象存储或加密移动硬盘
```

建议保留最近 30 份日备份、12 份月备份；每次备份记录时间、软件版本、数据版本和校验结果。备份完成后必须实际做一次恢复测试，不能只看“备份成功”提示。

## 7. 新软件上线流程

1. 给软件分配 `${APP_ID}`、子域名、内部端口和独立目录。
2. 创建 `data`、`backup`、`config`、`secrets`，设置最小权限。
3. 加入公共 Docker 网络，编写本软件 Compose 文件。
4. 在 Caddy 和 Cloudflare 中添加唯一的子域名路由。
5. 通过 `/health`、`/api/version` 或软件自带检查确认容器正常。
6. 创建第一份本机备份和一份异机备份。
7. 测试登录、写入、重启、备份、恢复和域名访问。
8. 把部署信息登记到下面的“软件资产卡”，再交付使用。

## 8. 更新流程

### 8.1 普通应用更新

1. 查看当前版本、容器配置、数据目录和备份状态。
2. 先执行应用层备份，再执行数据库专用导出。
3. 阅读新版本迁移说明，确认是否需要升级数据库结构。
4. 拉取新镜像或新代码，不删除 `data`、`backup` 和 `secrets`。
5. 使用 `docker compose up -d` 重建应用容器；只重建本软件服务。
6. 检查日志、健康接口、登录和一条写入/读取流程。
7. 保留旧镜像和最近备份，确认稳定后再清理。

### 8.2 SafeVault 类文件部署应用

如果软件不是镜像更新，而是挂载目录运行，更新时只覆盖程序文件，例如：

```text
dist/
server/
package.json
```

`data/`、`backup/`、`.env`、`secrets/` 和 Caddy 配置必须保留。替换后重启原容器，再验证版本接口和用户数据数量。

## 9. 服务器迁移流程

### 9.1 迁移前

- 列出所有软件、域名、容器、端口、数据目录、备份目录和秘密配置；
- 暂停高风险写入，执行最后一次应用层备份；
- 导出数据库或软件专用备份，并检查文件大小、时间和校验值；
- 保留旧服务器、旧磁盘、旧 DNS 和旧快照，不要先销毁。

### 9.2 迁移中

- 在新服务器按原软件标识创建同样的目录结构；
- 先部署软件和数据，再部署 Caddy/DNS；
- 恢复 `data`、`backup` 和必要的 `secrets`，不要注册空账号替代旧账号；
- 使用临时域名或 hosts 先测试，不要立即切换全部 DNS；
- 核对版本、账号数、条目数、最近更新时间和备份状态。

### 9.3 切换与验收

- 先切换一个低风险子域名，确认 HTTPS、登录、读写和备份；
- 再切换其他软件的 DNS/Tunnel 路由；
- 监控 24 至 72 小时，确认日志、资源、同步和备份正常；
- 所有软件完成验收后，才释放旧服务器和旧 DNS；
- 将最终地址、迁移日期、版本和回滚位置写回软件资产卡。

### 9.4 回滚

如果新服务器出现账号不存在、数据数量异常、写入失败或备份失败：

1. 立即停止新端写入；
2. 将 DNS/Tunnel 切回旧端；
3. 不要在新旧两端同时继续修改；
4. 对比迁移前后的数据和版本；
5. 修复后重新执行迁移验收。

## 10. 软件资产卡（每个软件复制一份）

```yaml
app_id: "${APP_ID}"
display_name: "${APP_NAME}"
repository: "${REPOSITORY_URL}"
production_version: "${VERSION}"
primary_url: "https://${APP_ID}.${ROOT_DOMAIN}"
api_url: "https://api-${APP_ID}.${ROOT_DOMAIN}"
server_provider: "OCI / NAS / other"
container_name: "${APP_ID}"
compose_file: "/opt/apps/${APP_ID}/compose.yml"
data_dir: "/opt/apps/${APP_ID}/data"
backup_dir: "/opt/apps/${APP_ID}/backup"
secret_location: "外部密码管理器或 secrets 文件，不进 GitHub"
backup_target: "另一台 NAS / 对象存储 / 离线磁盘"
sync_mode: "主备 / 应用层同步 / 定时导出"
primary_endpoint: "${PRIMARY_ENDPOINT}"
secondary_endpoint: "${SECONDARY_ENDPOINT}"
health_check: "${HEALTH_CHECK_URL}"
last_backup: "YYYY-MM-DD HH:mm"
last_restore_test: "YYYY-MM-DD HH:mm"
rollback_location: "${OLD_SERVER_OR_SNAPSHOT}"
owner: "${OWNER}"
notes: "${SPECIAL_MIGRATION_NOTES}"
```

## 11. 迁移完成检查清单

- [ ] 每个软件都有独立子域名、容器、数据目录和备份目录
- [ ] 公网只开放 HTTPS 入口，业务端口没有直接暴露
- [ ] Caddy、Cloudflare Tunnel 和容器路由一一对应
- [ ] 主数据、本机备份、异机备份均存在
- [ ] 备份已经做过真实恢复测试
- [ ] 更新没有删除或覆盖数据、备份和密钥
- [ ] 主备端点账号、版本和数据版本已经核对
- [ ] 新服务器完成登录、读写、同步、重启和恢复测试
- [ ] 旧服务器、旧 DNS 和旧快照仍可回滚
- [ ] 软件资产卡已更新并提交到文档仓库

## 12. SafeVault 当前实例对照

以下仅是本项目的实例，不要直接复制给其他软件：

```text
nas.985251.xyz       -> 极空间 Cloudflare Tunnel -> SafeVault NAS 容器
safevault.985251.xyz -> 甲骨文云公共 Caddy     -> 独立 SafeVault 容器
```

其他软件应改成自己的 `${APP_ID}.${ROOT_DOMAIN}`，并创建自己的 `data`、`backup` 和同步方案。
